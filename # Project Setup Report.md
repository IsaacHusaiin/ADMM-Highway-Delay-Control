
## 1. Project Goal

This project builds a traffic-control simulation for a short freeway corridor using an 8-cell Cell Transmission Model. The goal is to compare the original field-observed ramp-release behavior against controlled ramp-metering policies.

The project does **not** only look at freeway delay. It also tracks ramp queues, local ramp delay, fairness across ramps, safe-capacity violations, physical-capacity violations, and spillback.

---

## 2. Main Files

### `Benchmark_calculation.ipynb`

This is the main source-of-truth notebook.

It loads the PeMS traffic data, extracts the selected corridor, builds the 8-cell CTM setup, computes the benchmark baseline, and exports the shared input file used by the other notebooks. The exported object includes simulation settings, initial states, time-series inputs, corrected capacities, ramp metadata, free-flow travel times, official benchmark totals, and normalization denominators.

In simple terms:

```
Benchmark_calculation.ipynb = builds the official baseline and exports shared inputs
```

---

### `Benchmark.py`

This is the clean Python version of the benchmark simulation.

It loads `shared_benchmark_inputs.pkl`, reruns the observed-release benchmark, prints the final mainline states, final ramp queues, spillback, accumulated totals, and checks that the reproduced totals match the official benchmark totals.

In simple terms:

```
Benchmark.py = standalone validation script for the benchmark
```

This file is useful because it proves the benchmark can be reproduced outside Jupyter.

---

### `Greedy_ADMM.ipynb`

This notebook implements the one-step Greedy ADMM controller.

It loads the shared benchmark inputs exported by the benchmark notebook, then solves a ramp-metering optimization at each timestep using only the current traffic state. The notebook defines the ramp-side objective, freeway-side objective, ADMM update functions, ramp-meter capacity, and one-step solver.

In simple terms:

```
Greedy_ADMM.ipynb = one-step ADMM controller
```

This is the simpler ADMM controller because it does not look several steps into the future.

---

### `ADMM_MPC.ipynb`

This notebook implements the ADMM-MPC controller.

It uses the same CTM setup and benchmark inputs, but instead of optimizing only one timestep, it solves over a short future horizon. The notebook includes horizon-based ramp releases, warm starts, dual variables, ADMM convergence tracking, and stores both the applied first control and the full MPC plan.

In simple terms:

```
ADMM_MPC.ipynb = lookahead ADMM controller
```

This is the main advanced controller because it can anticipate future congestion.

---

### `fixed_policy.ipynb`

This notebook tests simple fixed ramp-metering policies.

Instead of solving an optimization problem, it scales the observed ramp release by a fixed multiplier. This gives a simple comparison case between the original benchmark and the optimized ADMM-MPC controller. The fixed-policy ablation is used to check whether the optimized controller is doing something smarter than simply releasing fewer ramp vehicles.

In simple terms:

```
fixed_policy.ipynb = simple fixed-release comparison
```

## 3. Shared Input Design

The project uses one shared input file:

```
shared_benchmark_inputs.pkl
```

This file is generated by `Benchmark_calculation.ipynb`.

The reason for this file is consistency. All models should use the same:

```
mainline initial stateramp initial queuesramp arrival seriesobserved release seriesoff-ramp flow seriesboundary inflow seriesdoorway capacitiessafe-threshold capacitiesphysical capacitiesramp storage limitsfree-flow travel timesobjective weightsnormalization denominators
```

This prevents the benchmark, Greedy ADMM, and ADMM-MPC notebooks from silently using different assumptions. The project specifically treats ramp arrivals as fixed external demand, not as something recomputed from the optimizer’s release decisions.

## 4. Corridor Setup

The corridor is modeled as:

```

```

The five ramps are mapped into freeway cells as:

```
u1 → Cell 2u2 → Cell 4u3 → Cell 5u4 → Cell 6u5 → Cell 7
```

This ramp-to-cell mapping is exported with the shared benchmark inputs.

## 5. CTM Modeling Setup

The freeway is simulated using a Cell Transmission Model.

Each cell has:

```
vehicle countsending capacityreceiving capacitydoorway capacitysafe-threshold capacityphysical storage capacityoff-ramp flowmainline inflowmainline outflow
```

The model updates traffic every 30 seconds. Vehicles move from one cell to the next based on sending and receiving limits.

The final cell discharges traffic out of the modeled corridor.

---

## 6. Ramp Queue Setup

Each ramp has a queue.

At every timestep:

```
new ramp queue = old queue + ramp arrivals - ramp release
```

If the queue exceeds the maximum ramp storage, the queue is capped and the extra vehicles are counted as spillback.

This means the model separates:

```
stored ramp queuespillback beyond ramp storage
```

The notebook documentation states that ramp queues have finite storage, and excess vehicles are recorded as spillback.

---

## 7. Main Assumptions

### Assumption 1: Ramp arrivals are estimated

PeMS ramp detectors measure released/discharged vehicles, not the true number of vehicles that wanted to enter the ramp.

Because of that, ramp arrivals are estimated using a multiplier applied to observed ramp release. The project notes that this is an assumption and should be tested with sensitivity analysis.

---

### Assumption 2: Ramp arrivals are external demand

Ramp arrivals are fixed input demand.

They are **not** recomputed from the optimized ramp release. This is important because the controller should not be allowed to reduce demand just by releasing fewer vehicles.

---

### Assumption 3: Negative mainline delay is clamped to zero

The original state-based delay formula can become slightly negative because the free-flow travel time is larger than the 30-second timestep for some cells.

Since delay cannot physically be negative, the project clamps per-cell delay at zero. This fix is applied consistently across the benchmark, ADMM, and ADMM-MPC models.

---

### Assumption 4: Safe capacity and physical capacity are different

The model separates:

```
safe-threshold capacityphysical storage capacity
```

The safe threshold represents an operational congestion limit. The physical capacity represents the hard storage limit of the cell.

So a cell can exceed the safe threshold without exceeding physical capacity.

---

### Assumption 5: Spillback is penalized separately

If ramp queues exceed storage, the excess is treated as spillback onto the local road network.

Spillback is not ignored. It is included as a separate penalty term.

---

### Assumption 6: The same inputs must be used across all models

Benchmark, Greedy ADMM, ADMM-MPC, and fixed-policy comparisons must use the same initial states, capacities, arrivals, ramp storage, and delay definitions.

This is why the project exports and reloads `shared_benchmark_inputs.pkl`.

---

## 8. Objective Function Setup

The project objective combines several terms:

```
mainline delaylocal ramp delayfairness penaltydoorway penaltysafe-threshold penaltyphysical-capacity penaltyspillback penalty
```

Mainline delay measures freeway congestion.

Local delay measures waiting on ramps.

Fairness measures whether some ramps are being overloaded more than others.

Doorway penalty measures excessive inflow into a cell.

Safe-threshold penalty measures operational congestion above the safe limit.

Physical-capacity penalty measures hard storage violations.

Spillback penalty measures ramp demand that exceeds ramp storage.

---

## 9. Normalization Setup

The project normalizes objective terms using benchmark denominators.

This is done because the raw terms have different scales. For example, delay values and squared penalty values can be very different numerically.

The benchmark notebook computes these denominators from the official benchmark history and exports them with the shared input file.

---

## 10. Controller Setup

### Benchmark

The benchmark uses observed ramp releases.

It represents the field-observed no-control or existing-control baseline.

---

### Greedy ADMM

Greedy ADMM optimizes one timestep at a time.

It reacts to the current state but does not plan far ahead.

---

### ADMM-MPC

ADMM-MPC optimizes over a future horizon.

It applies only the first control action, then moves forward and repeats. The notebook stores both the applied control and the full planned horizon.

---

### Fixed Policy

The fixed-policy notebook applies simple scaled ramp releases.

It is not adaptive. It is used as an ablation test to compare against ADMM-MPC.

## 12. Important Reporting Note

The results should not be described as “ADMM-MPC is universally better.”

The correct framing is:

```
ADMM-MPC creates a freeway-ramp tradeoff.
```

The controller can reduce freeway-side congestion by holding more vehicles on ramps, but this can increase ramp queue pressure and spillback. The notebook explicitly warns against describing ADMM-MPC as universally better or as having no downside.
